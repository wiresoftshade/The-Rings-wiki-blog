Введение
------------

Привет, меня зовут [Гленн Фидлер](https://gafferongames.com) и добро пожаловать в **Game Physics**

В [предыдущей статье](integration_basics_ru.md) мы обсуждали, как интегрировать уравнения движения с помощью численного интегратора. Интегрирование звучит сложно, но это всего лишь способ продвинуть вашу физическую симуляцию вперёд на небольшой промежуток времени, называемый «дельта-временем» (или сокращённо dt).

Но как выбрать значение дельты-времени? Это может показаться тривиальным, но на самом деле существует множество способов сделать это, каждый со своими сильными и слабыми сторонами — так что читайте дальше!

Фиксированное дельта-временем
----------------

Самый простой способ сделать шаг вперёд — использовать фиксированную дельту-времени, например, 1/60 секунды:

```cpp
double t = 0.0;
double dt = 1.0 / 60.0;

while ( !quit )
{
    integrate( state, t, dt );
    render( state );
    t += dt;
}
```

Во многих отношениях этот код идеален. Если вам повезло, что ваше дельта-время совпадает с частотой обновления экрана, и вы можете гарантировать, что цикл обновления занимает меньше одного кадра реального времени, то у вас уже есть идеальное решение для обновления вашей физической симуляции, и вы можете дальше не читать эту статью.

Но в реальном мире вы можете не знать частоту обновления экрана заранее. VSYNC может быть отключена, или вы работаете на медленном компьютере, который не может обновлять и рендерить кадр достаточно быстро, чтобы отображать его с частотой 60 кадров в секунду.

В этих случаях ваша симуляция будет выполняться быстрее или медленнее, чем вы планировали.

Переменное дельта-время
-------------------

Исправить это *кажется* простым. Просто измерьте длительность предыдущего кадра, а затем передайте это значение в качестве дельта-времени для следующего кадра. Это, конечно, имеет смысл, поскольку если компьютер слишком медленный для обновления с частотой 60 Гц и вынужден снизить её до 30 кадров в секунду, вы автоматически передадите 1/30 в качестве дельта-времени. То же самое происходит при частоте обновления дисплея 75 Гц вместо 60 Гц или даже в случае, когда VSYNC отключен на быстром компьютере:

```cpp
double t = 0.0;

double currentTime = hires_time_in_seconds();

while ( !quit )
{
    double newTime = hires_time_in_seconds();
    double frameTime = newTime - currentTime;
    currentTime = newTime;

    integrate( state, t, frameTime );
    t += frameTime;

    render( state );
}
```    

Но у этого подхода есть огромная проблема, которую я сейчас объясню. Проблема в том, что поведение вашей физической симуляции зависит от передаваемой вами дельты времени. Эффект может быть едва заметным, например, ваша игра будет немного отличаться в зависимости от частоты кадров, или же он может быть настолько экстремальным, что ваша симуляция пружины будет взрываться в бесконечность, быстро движущиеся объекты будут пробивать стены, а игроки — проваливаться сквозь пол!

Одно можно сказать наверняка: совершенно нереалистично ожидать, что ваша симуляция будет правильно обрабатывать _любую_ переданную ей дельту времени. Чтобы понять, почему, представьте, что произойдёт, если вы передадите 1/10 секунды в качестве дельты времени? Как насчёт одной секунды? Десяти секунд? 100 секунд? В конце концов, вы найдёте точку невозврата.

Частично фиксированный временной шаг
-------------------

Гораздо реалистичнее сказать, что ваша симуляция хорошо себя ведёт, только если дельта времени меньше или равна некоторому максимальному значению. На практике это обычно значительно проще, чем пытаться сделать симуляцию безошибочной в широком диапазоне значений дельты времени.

Зная это, вот простой трюк, который поможет вам никогда не передавать значение дельты времени, превышающее максимальное, при этом сохраняя корректную скорость работы на разных машинах:

```cpp
double t = 0.0;
double dt = 1 / 60.0;

double currentTime = hires_time_in_seconds();

while ( !quit )
{
    double newTime = hires_time_in_seconds();
    double frameTime = newTime - currentTime;
    currentTime = newTime;
            
    while ( frameTime > 0.0 )
    {
        float deltaTime = min( frameTime, dt );
        integrate( state, t, deltaTime );
        frameTime -= deltaTime;
        t += deltaTime;
    }

    render( state );
}
```

Преимущество такого подхода заключается в том, что теперь у нас есть верхняя граница для дельта-времени. Она никогда не превышает этого значения, поскольку в этом случае мы делим временной шаг. Недостаток же заключается в том, что теперь мы выполняем несколько шагов за обновление дисплея, включая один дополнительный шаг, который используется для потребления оставшегося времени кадра, не делящегося на dt. Это не проблема, если вы ограничены в скорости рендеринга, но если ваша симуляция — самая ресурсоёмкая часть вашего кадра, вы можете столкнуться с так называемой «спиралью смерти».

Что такое «спираль смерти»? Это происходит, когда ваша физическая симуляция не успевает выполнять требуемые шаги. Например, если вашей симуляции говорят: «Хорошо, пожалуйста, смоделируйте физику на X секунд», и если на это уходит Y секунд реального времени, где Y > X, то не нужно быть Эйнштейном, чтобы понять, что со временем ваша симуляция отстаёт. Это называется «спиралью смерти», потому что отставание заставляет ваше обновление имитировать больше шагов, чтобы наверстать упущенное, что приводит к ещё большему отставанию, что, в свою очередь, заставляет вас имитировать ещё больше шагов…

Итак, как же этого избежать? Чтобы обеспечить стабильное обновление, я рекомендую оставить некоторый запас. Вам действительно нужно убедиться, что обновление физической симуляции на протяжении X секунд занимает _значительно меньше_ X секунд реального времени. Если это возможно, ваш физический движок сможет «догнать» любой временный скачок, симулируя больше кадров. В качестве альтернативы, вы можете ограничить максимальное количество шагов на кадр, и симуляция будет казаться замедляющейся при высокой нагрузке. Возможно, это лучше, чем стремительное падение в спираль, особенно если большая нагрузка — это всего лишь временный скачок.

Освободите физику
----------------

Теперь давайте сделаем ещё один шаг. Что, если вам нужна точная воспроизводимость от одного запуска к другому при одних и тех же входных данных? Это удобно при попытке объединить в сеть вашу физическую симуляцию с использованием детерминированного шага, но также, как правило, приятно знать, что ваша симуляция ведёт себя абсолютно одинаково от запуска к запуску, без какой-либо возможности изменения поведения в зависимости от частоты кадров рендеринга.

Но вы спрашиваете, зачем для этого нужна полностью фиксированная дельта-время? Разве полуфиксированная дельта-время с небольшим шагом остатка «достаточно хороша»? И да, вы правы. В большинстве случаев она _достаточно хороша_, но не _совсем одинакова_ из-за ограниченной точности арифметики с плавающей запятой.

Таким образом, нам нужно лучшее из обоих миров: фиксированное значение дельты-времени для симуляции и возможность рендеринга с разной частотой кадров. Эти две вещи кажутся совершенно противоречащими друг другу, и так и есть, если только мы не найдём способ разделить частоту кадров симуляции и рендеринга.

Вот как это сделать. Продвигайте физическую симуляцию вперёд с фиксированным шагом dt, следя при этом за тем, чтобы она соответствовала значениям таймера, поступающим от рендерера, чтобы симуляция продвигалась с правильной скоростью. Например, если частота кадров дисплея составляет 50 кадров в секунду, а симуляция выполняется со скоростью 100 кадров в секунду, то нам нужно выполнять два шага физики при каждом обновлении дисплея. Просто.

Что, если частота кадров дисплея составляет 200 кадров в секунду? В этом случае нам нужно выполнять половину шага физики при каждом обновлении дисплея, но мы не можем этого сделать, поэтому мы должны продвигаться с постоянным dt. Поэтому мы делаем один шаг физики каждые два обновления дисплея.

Ещё сложнее: что, если частота кадров дисплея составляет 60 кадров в секунду, но мы хотим, чтобы наша симуляция работала со скоростью 100 кадров в секунду? Простого решения этой проблемы нет. Что, если VSYNC отключена, а частота кадров дисплея колеблется от кадра к кадру?

Если у вас просто взорвалась голова, не волнуйтесь, всё, что нужно для решения этой проблемы, — это изменить точку зрения. Вместо того чтобы думать, что у вас есть определённое количество времени кадра, которое необходимо симулировать перед рендерингом, переверните свою точку зрения и подумайте об этом так: рендерер **производит время**, а симуляция **потребляет** его дискретными шагами размером dt.

Например:

```cpp
double t = 0.0;
const double dt = 0.01;

double currentTime = hires_time_in_seconds();
double accumulator = 0.0;

while ( !quit )
{
    double newTime = hires_time_in_seconds();
    double frameTime = newTime - currentTime;
    currentTime = newTime;

    accumulator += frameTime;

    while ( accumulator >= dt )
    {
        integrate( state, t, dt );
        accumulator -= dt;
        t += dt;
    }

    render( state );
}
```

Обратите внимание, что в отличие от полуфиксированного временного шага, мы всегда интегрируем только с шагами размером dt, поэтому в общем случае в конце каждого кадра остаётся некоторое несимулированное время. Это оставшееся время передаётся следующему кадру через переменную-аккумулятор и не отбрасывается.

Последний штрих
--------------

Но что делать с этим оставшимся временем? Кажется неправильным, не правда ли?

Чтобы понять, что происходит, рассмотрим ситуацию, когда частота кадров дисплея составляет 60 кадров в секунду, а физика — 50 кадров в секунду. Умножителя нет, поэтому аккумулятор заставляет симуляцию попеременно выполнять один, а иногда и два шага физики за кадр, когда остатки «накапливаются» выше dt.

Теперь учтите, что у большинства кадров рендеринга в аккумуляторе останется небольшой остаток времени кадра, который невозможно смоделировать, поскольку он меньше dt. Это означает, что мы отображаем состояние физической симуляции в момент времени, немного отличающийся от времени рендеринга, что приводит к едва заметному, но визуально неприятному подтормаживанию физической симуляции на экране.

Одним из решений этой проблемы является интерполяция между предыдущим и текущим состоянием физики на основе оставшегося времени в аккумуляторе:

```cpp
double t = 0.0;
double dt = 0.01;

double currentTime = hires_time_in_seconds();
double accumulator = 0.0;

State previous;
State current;

while ( !quit )
{
    double newTime = time();
    double frameTime = newTime - currentTime;
    if ( frameTime > 0.25 )
        frameTime = 0.25;
    currentTime = newTime;

    accumulator += frameTime;

    while ( accumulator >= dt )
    {
        previousState = currentState;
        integrate( currentState, t, dt );
        t += dt;
        accumulator -= dt;
    }

    const double alpha = accumulator / dt;

    State state = currentState * alpha + 
        previousState * ( 1.0 - alpha );

    render( state );
}
```

Это _выглядит_ сложно, но вот простой способ представить это. Любой остаток в аккумуляторе фактически является мерой того, сколько времени требуется, чтобы выполнить следующий полный шаг физики. Например, остаток dt/2 означает, что мы находимся на полпути между текущим шагом физики и следующим. Остаток 0.1\*dt означает, что обновление составляет 1/10 расстояния между текущим и следующим состоянием.

Мы можем использовать это значение остатка для получения коэффициента смешивания между предыдущим и текущим физическим состоянием, просто разделив его на dt. Это даёт значение альфа в диапазоне \[0,1\], которое используется для выполнения линейной интерполяции между двумя физическими состояниями для визуализации текущего состояния. Такая интерполяция легко выполняется как для отдельных значений, так и для векторных значений состояний. Вы даже можете использовать его с полной динамикой трёхмерного твёрдого тела, если сохраните ориентацию в виде кватерниона и примените сферическую линейную интерполяцию (SLERP) для перехода между предыдущей и текущей ориентацией.
