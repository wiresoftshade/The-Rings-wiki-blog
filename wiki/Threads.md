# Threads in UE

1. Game Thread
2. Render Thread
3. RHI Thread
4. Workers...

**Поток** (**Thread**) — это програмная абстракция. Создается и управляется ОС. Потоков может быть сотни. Не привязаны к ядру процессора.

**Ядро** (**Core**) — это реальный вычислительный блок процессора. Ядра работают одновременно. На каждом по одному потоку. Ядро может переключаться между потками. Получается в один момент работает столько потоков, сколько существует ядер на процессоре.

> [!IMPORTANT]
> **Важное замечание.** Render Thread работает на один кадр позади GameThread. Отсюда минимальный inputlag даже на 60fps. Это архитектурная особенность движка.

## Worker threads

Это пулл различных потоков, которые занимаются фоновыми задачами. В этом потоке, например, загружаются ассеты, когда просишь его загрузиться с soft reference. Просчеты navigation-mesh.

## TaskGraph

Планировщик задач. Описываешь задачу и зависимости — TaskGraph сам решает на коком Worker thread и в каком порядке задачу ввыполнить.

- **Animation Graph** — часть вычислений анимации
- **Async Asset Loading** — загрузка ассетов без хитча
- **Твои задачи через AsyncTask** — математика, парсинг
- **NavMesh Build** — просчет пути в фоне

## Что нельзя делать вне Game Thread

- Spawn/Destroy Actor

    *Только Game Thread управляет жизненным циклом объектов.*

- Read/write Actor property

    *location, health, other any actor values — not thread-safe. Может появиться Race Condition\*.*

- Вызывать BlueprintCallable

    *Blueprint VM однопоточна — креш или неопределенное поведение.*    

- Использовать UObject API

    *Garbage collector не thread-safe — GC может удалить объект в любой момент.*

- GEngine->AddOnScreenDebugMessage

    *Даже вывод на экран — только с Game Thread.*

Из-за нарушения этих правил может появиться **краш** или неопределенное поведение, либо какие-то **случайные баги**, которые **невозможно воспроизвести стабильно**. Это самые неприятные, **самые отвратительные баги**. Все потому что в потоках так сложилось. 

## Что можно делать в WorkerTHread

- Читать иммутабельные данные

    *DaraAssets, таблици конфигов, статичные массивы — безопасно*

- Математика и алгоритмы

    *Pathfinding, генерация мира, парсинг JSON, сортировка — все сюда*

- Async IO / загрузка файлов

    *чтение с диска без блокировки Game Thread*

- FRunnable. Свой поток можно организовать
  
    *Для долгих фоновых задач: сетевой сервер, стриминг чанков. **Записывать риплей файл** без блокировки игрового треда*

*Race Condition*\* — это неопределенное поведение параллельных потоков, когда они выполняют одинаковые команды. Неизвестно кто выполнится раньше. От этого будет не определен результат. 

имеем (var == 0)

    var += 3; // task for thread A 
    var += 5; // task for thread B 

Потоки выполняются последовательно:

    // timeline
    [thread A ---]--------------
    --------------[thread B----]
    // здесь потоки выполнились строго последовательно, поэтому результатом будет: A:0+3=3 A передает результат. B:3+5=8 B передает результат. 
    
    Результат: 8.

Потоки выпольняются параллельно с Наложением:

    // timeline
    ---[thread A -------]-------
    ----------[thread B -------]
    // здесь потоки выполнились с наложением, поэтому результатом будет: A:0+3=3 A не передает результат. В берет переменную раньше B:0+5=5 
    
    Результат: B передает 5.

Потоки выпольняются параллельно с Наложением наоборот:

    // timeline
    ----------[thread A -------]
    ---[thread B -------]-------
    // здесь потоки выполнились с другим наложением, поэтому результатом будет: B:0+5=5 B не передает результат. A берет переменную раньше. A:0+3=3 
    
    Результат: А передает 3.

Еще один вариант: 

    // timeline
    ---[thread A --------------]
    -------[thread B ---]-------
    // здесь потоки разной длинны выполнились с таким наложением 
    
    Результат: А передает 3.

Каждый раз разный результат. Это называется **Race condition**.

Тогда вероятно RenderThread ждет GameThread или наоборот. Ищи через `UngealInsights -> CPU Track`.
